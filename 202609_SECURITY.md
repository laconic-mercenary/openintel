# openintel — Security Review, September 2026

Review date: 2026-09-07
Reviewed at: `26d9cee` (last commit 2026-06-17)
Scope: `apps/roverapi` (Go, both binaries), `apps/rover` (React client), `apps/landing`, `apps/test`, deployment config.

This document covers **security and security-adjacent findings only**. Functional
correctness bugs (viewport race conditions, longitude normalisation, retry-induced
duplicate comments, etc.) are real but out of scope here and tracked separately.

## Context

openintel's security model is sound in its fundamentals. The client encrypts with
PBKDF2-SHA256 (310,000 iterations) into AES-256-GCM, derives the key non-extractable,
and keeps it in IndexedDB; the key never leaves the browser. The Go backend only ever
receives `geohash`, `authorHash`, `encryptedPayload`/`encryptedText`, `imageKey`,
`timestampObfuscated`, and `rowKey` — content genuinely never reaches the server in
plaintext. The one deliberate plaintext field is `geohash` (~5x5 km cell), which the
privacy policy discloses accurately.

The findings below are therefore not architectural failures. They are gaps in a design
that is otherwise correct, and most have small, local fixes.

## Priority legend

| Level | Meaning |
|---|---|
| **P0** | Exploitable now, cross-tenant impact or account takeover. Fix before further feature work. |
| **P1** | Exploitable, bounded by an unguessable value or requires effort. Fix this cycle. |
| **P2** | Defence-in-depth failure, abuse vector, or hygiene issue with real consequences. |
| **P3** | Design tension or ineffective control. Decide and document rather than patch. |

## Findings

| # | Title | Priority | Problem | Consequence if not fixed | Proposed Fix | Affected modules |
|---|---|---|---|---|---|---|
| 1 | OData filter injection in comments table | **P0** | `IsValidIntelRowKey` validates length, the 20-digit prefix and the `-` separator, but never validates the 32-char digest suffix, so arbitrary bytes including `'` are accepted. `ListComments` interpolates that value straight into an OData filter: `fmt.Sprintf("PartitionKey eq '%s'", intelRowKey)`. | Any authenticated user can break out of the string literal and return **every comment row in the table for every user** — ciphertext, `AuthorHash` and `Geohash`. Comment text stays encrypted, but the geohashes are a cross-tenant location-privacy breach. | Require the digest suffix to be lowercase hex (and the legacy suffix to be a valid UUID) in `IsValidIntelRowKey`. A single character-class loop closes this permanently. Optionally also escape `'` at the repository layer as defence in depth. | `apps/roverapi/internal/validation/intel.go`, `apps/roverapi/internal/storage/table_comments.go:152` |
| 2 | Login token is deterministic and never expires | **P0** | `newAuthToken(email)` is a pure function of email + pepper with no random component, so the same email always yields the same token forever. That token is the `?x=` parameter in the emailed login link. | Anyone who captures a single login-link URL (browser history, forwarded mail, mail-scanner logs, a screenshot) holds a **permanent capability to read that account's login codes**. Combined with finding 3, they can trigger a code themselves via `/auth/email-link` and read it without ever touching the victim's inbox — full account takeover. | Generate a cryptographically random nonce per login request, store it alongside the code, and make it single-use (delete on redemption as well as on expiry). Keep the email hash only as the lookup key, not as the credential. | `apps/roverapi/pkg/auth/service.go:245` (`newAuthToken`), `:74` (`SendLoginCode`), `:151` (`VerifyLoginCode`), `:214` (`DeleteLoginCode`) |
| 3 | `/auth/get-code` has no origin check and no rate limiting | **P1** | The route is registered with bare `WithMethodCheck` instead of `applyMiddleware`, unlike every other auth route. It renders the current 6-digit OTP as HTML to any caller presenting a token. | Unlimited token guessing with no throttle, and no origin restriction. Amplifies finding 2 into a practical takeover path. The rendered page also has no `noindex`, so link previews and corporate mail scanners that fetch URLs can surface the code. | Wrap in `applyMiddleware`. Add per-token and per-IP rate limiting. Add `X-Robots-Tag: noindex` and `Referrer-Policy: no-referrer` to the response. Consider requiring a POST confirmation rather than rendering the code on GET. | `apps/roverapi/cmd/auth/main.go:351`, `:117` (`handleGetCode`) |
| 4 | Missing ownership check on image upload URL | **P1** | `handleGetImageUploadURL` authenticates the cookie then **discards the identity** (`_, emailErr := server.EmailFromCookie(...)`) and calls `GetImageUploadURL(ctx, key)` with no `emailHash`. Every sibling handler scopes by `emailHash + geohash` as the partition key. | Any authenticated user holding another user's rowKey obtains a **presigned PUT URL for that user's image object** and can overwrite it. This is a destructive cross-tenant write. Bounded only by rowKey unguessability — but rowKeys appear in URLs, in application logs, and in plaintext export files. | Compute `emailHash` from the cookie, load the intel row by `emailHash + geohash` + rowKey to prove ownership, and only then presign. Mirror the pattern already used in `AddComment`. | `apps/roverapi/cmd/rover/main.go:336-370`, `apps/roverapi/pkg/rover/service.go:140` |
| 5 | Missing ownership check on comment listing | **P1** | `handleListComments` likewise discards the authenticated identity and calls `ListComments(ctx, key)` with no `emailHash`. The comments table is partitioned by `intelRowKey` alone, not by owner. | Any authenticated user holding a rowKey reads that intel's full comment thread — ciphertext, author hashes and geohash. Content stays encrypted, but the metadata graph and location leak. | Verify ownership before listing, exactly as `AddComment` does at `service.go:292` (`GetPrivateIntelMetadata(emailHash+geohash, rowKey)` first). Consider re-partitioning the comments table to include `emailHash` so the check is structural rather than procedural. | `apps/roverapi/cmd/rover/main.go:443-487`, `apps/roverapi/pkg/rover/service.go:312`, `apps/roverapi/internal/storage/table_comments.go` |
| 6 | Unauthenticated Argon2id CPU/memory amplification | **P1** | `newAuthToken` invokes Argon2id **twice** per call at 64 MB / 3 iterations. It is called from `SendLoginCode`, `VerifyLoginCode` and `DeleteLoginCode`, so one successful login costs 4 x 64 MB. Both `/auth/email-link` and `/auth/code-login` are unauthenticated, and the rate limiter only engages *after* the token lookup succeeds. | On a Consumption-plan Function (~1.5 GB), roughly 20 concurrent requests exhaust memory. A trivial unauthenticated denial-of-service against the entire login path, and a direct cost amplifier on consumption billing. | Derive the token once per request and pass it down rather than recomputing in each method. Add pre-auth per-IP rate limiting ahead of any Argon2 work. Re-evaluate whether Argon2 is the right primitive for a deterministic lookup key at all — an HMAC would be sufficient and ~free once finding 2 introduces a random nonce. | `apps/roverapi/pkg/auth/service.go:245`, `apps/roverapi/internal/security/hashing.go:22`, `apps/roverapi/cmd/auth/main.go:350-354` |
| 7 | No security headers anywhere; no CSP | **P1** | Zero occurrences of `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` or HSTS across nginx config, both HTML entry points, and the landing container. | The entire security model depends on the JavaScript on the page being the JavaScript you shipped. With no CSP there is nothing constraining script origins, so any injection or supply-chain compromise can exfiltrate the decryption password or plaintext directly. Missing `Permissions-Policy` is also notable for an app that requests camera and geolocation. | Add a strict CSP to `nginx.conf` and the landing container (`script-src 'self'` plus the pinned CDN origins actually required by web-llm; `connect-src` limited to self, MapTiler and the object store). Add `nosniff`, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `Permissions-Policy: camera=(self), geolocation=(self)`, and HSTS. | `apps/rover/nginx.conf`, `apps/rover/index.html`, `apps/landing/Dockerfile`, `apps/landing/index.html` |
| 8 | Origin check fails open on missing `Origin` header | **P2** | `HasAllowedOrigin` returns `true` when the `Origin` header is absent, logging "allowing (proxied or same-origin request)". An allowlist that defaults to allow. | Any non-browser client bypasses the check by simply omitting the header, which is what makes finding 6 reachable. Browser CSRF is *currently* blocked by the `SameSite=Strict; HttpOnly; Secure` cookie, so this is a defence-in-depth failure rather than an exploitable CSRF today — but it silently becomes one if the cookie policy is ever relaxed. | Fail closed for state-changing methods. Allow a missing `Origin` only for `GET`/`HEAD`, or require `Sec-Fetch-Site` where present. Keep the `SameSite=Strict` cookie as the primary control. | `apps/roverapi/internal/server/http.go:32-40` |
| 9 | Auth token written to application logs | **P2** | The auth token is logged at `Error`/`Warn` level in three places. The inline comment reasons this is safe because a non-existent token cannot be compromised. | Given finding 2, the token is a **permanent credential**, so logging it writes reusable account-access material into log storage regardless of whether the row currently exists. Log retention then becomes a credential store. | Stop logging the token entirely; log a truncated hash if correlation is needed. Revisit once finding 2 makes tokens single-use and random. | `apps/roverapi/pkg/auth/service.go:136`, `:145`, `:170` |
| 10 | No rate limit on `/auth/email-link` | **P2** | The endpoint is unauthenticated and sends email to any address supplied. The OSI/blocklist check assesses address reputation, not request rate. There is no per-IP throttle and no CAPTCHA. | An attacker can send login emails to arbitrary third parties on demand — an email-bombing vector, a sender-reputation risk for the `openintel.to` domain, and a direct cost on the Resend account. `ErrLoginCodeAlreadySent` also lets an attacker lock a victim out of requesting their own code for the 300 s expiry window. | Add per-IP and per-address rate limiting ahead of the send. Consider a proof-of-work or CAPTCHA on first contact from an unseen IP. | `apps/roverapi/cmd/auth/main.go:221` (`handleEmailLink`), `apps/roverapi/pkg/auth/service.go:74` |
| 11 | Stale compiled binaries committed to the repository | **P2** | `deploy/authapi/authapi` (9.6 MB) and `deploy/roverapi/roverapi` (12.9 MB) are tracked in git, last updated at `1029689` (2026-04-07). Twelve subsequent commits changed `apps/roverapi`. They are listed in `.gitignore`, but ignore rules do not apply to already-tracked files. | Anyone deploying from the tree as committed ships a backend that is two months behind the source, missing comments, tags, pinning and direct-to-R2 upload. Separately, ~22 MB of stripped, unauditable ELF blobs in the history of a project whose value proposition is verifiable client-side crypto is a supply-chain smell no reviewer can diff. | `git rm --cached` both paths; the existing `.gitignore` rules take effect immediately. Add `GOARCH=amd64` to `deploy.sh` (it currently inherits the host arch — arm64 on this machine — while the committed artifacts are x86-64). Rewriting history to drop the blobs is optional and depends on how much clone size matters. | `apps/roverapi/deploy/authapi/authapi`, `apps/roverapi/deploy/roverapi/roverapi`, `apps/roverapi/deploy.sh`, `.gitignore` |
| 12 | Timestamp obfuscation provides no real protection | **P3** | `handleStoreIntel` adds a per-user constant offset derived from `HMAC(email, timestampPepper)[:4]` (0–49.7 days). Because the offset is constant per user, ordering, intervals and time-of-day patterns all survive. Decisively, **Azure Table Storage stamps every entity with its own server-side `Timestamp` property** regardless of what the application writes. | The only adversary this control could defend against is the operator, and the storage platform hands the operator the true insert time anyway. The mechanism creates a false sense of protection and adds a pepper to the secret inventory for no benefit. | Decide explicitly: either remove it and document that creation time is visible to the operator, or move to a design that actually hides it (client-side jitter written into the encrypted payload, with a coarse or absent server-side ordering key). The application-level intent is already correct — `service.go:124` zeroes the real timestamp before storage. | `apps/roverapi/cmd/rover/main.go:155`, `apps/roverapi/pkg/rover/service.go:124`, `apps/roverapi/internal/storage/table.go:84` |
| 13 | Export writes fully decrypted data to disk | **P3** | `exportIntel` decrypts descriptions, tags, coordinates, images and comments and writes them as unencrypted JSON via a browser download. | The single point where the threat model inverts: plaintext leaves the encrypted envelope onto the user's filesystem, cloud-synced Downloads folders included. Nothing in the UI copy warns about this. Note the exported rowKeys also feed findings 4 and 5. | Likely intentional and legitimate as a user-controlled action — but surface it. Add an explicit warning in the export dialog, and consider offering a passphrase-encrypted export as the default with plaintext as an opt-in. | `apps/rover/src/utils/export.js:51`, `apps/rover/src/components/ExportIntelDialog.jsx` |

## Suggested remediation order

1. **Finding 1** — smallest fix, largest blast radius removed. One validation loop.
2. **Findings 4 and 5** — same pattern, same afternoon; both are two-line changes that
   reuse the ownership check already present in `AddComment`.
3. **Findings 2, 3, 9** — the auth-token rework. These are coupled and should land together.
4. **Findings 6 and 10** — rate limiting and Argon2 call reduction, naturally paired with the above.
5. **Finding 7** — CSP and headers. Independent of everything else; can proceed in parallel.
6. **Findings 8, 11** — hygiene.
7. **Findings 12, 13** — decisions to make and document rather than code to write.

## Standing gap

There is **no test coverage anywhere in this repository** — no `*_test.go`, no
`*.test.js`, no `*.spec.js` — and no CI (the Azure Static Web Apps workflow was removed
in `bcc9a1a` and never replaced). The modules with zero coverage are precisely the ones
in this document: `internal/validation`, `internal/security`, `internal/geo`,
`internal/server`, and client-side `crypto.js` / `keystore.js`.

This matters more here than in most projects. If key derivation ever regresses in a way
that still round-trips locally but writes garbage, users lose their data permanently by
design — there is no password reset and no server-side plaintext to recover from. Every
fix in this document should land with a test, and a minimal CI workflow
(`go build`, `go vet`, `npm run lint`, `vite build`) should precede the rest of the work.
